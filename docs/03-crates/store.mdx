`starlet-store` (lib `starlet_store`) owns every byte that touches disk: one
SQLite file, one `sqlx` connection pool, the schema, the migrations, and the
DAOs for repos, tags, groups, key/value state, AI-run history, and the FTS5
index. It is the only crate in the workspace that knows SQL exists.

It must never rank, parse queries, or fuzzy-match — that is
[`core`](/crates/core), and the two halves are combined in `starlet_core::rank`
(`crates/store/src/fts.rs:1-4`). It must never block the UI thread. And it must
never resolve the `STARLET_DB` override itself: the crate offers
`default_database_path()` and nothing more, while the binary reads the env var
(`crates/app/src/main.rs:45-48`).

::::info[Every method is `async`, and none of them may run in `render`]
"Every method here is `async` and runs on the caller's Tokio runtime. The UI
never calls these directly from `render`; it goes through the background
executor and applies results on the application thread"
(`crates/store/src/lib.rs:7-9`). That is the crate's defining constraint —
see [Runtime](/architecture/runtime) for the bridge that enforces it.
::::

## Opening a store

```rust crates/store/src/lib.rs
pub async fn Store::open(path: impl AsRef<Path>) -> Result<Self>   // :61
pub async fn Store::open_in_memory() -> Result<Self>               // :81
pub fn       Store::pool(&self) -> &Pool<Sqlite>                   // :115
pub async fn Store::close(&self)                                   // :120
pub fn       default_database_path() -> Result<PathBuf>            // :130
```

`Store` is `Clone + Debug` and wraps exactly one `Pool<Sqlite>`
(`crates/store/src/lib.rs:54-57`), so cloning it is free and every clone shares
the same pool.

**File-backed configuration** (`crates/store/src/lib.rs:66-75`), in full:

| Setting | Value | Why |
| --- | --- | --- |
| `journal_mode` | `Wal` | The sync worker writes while the UI reads (`:3-5`) |
| `synchronous` | `Normal` | Documented safe pairing with WAL. A crash can lose the tail of the last transaction, which for a rebuildable mirror of GitHub is not worth an fsync per commit (`:70-72`) |
| `foreign_keys` | `true` | `ON DELETE CASCADE` is inert without it |
| `busy_timeout` | 10 s | Writer/reader contention waits instead of erroring |
| `create_if_missing` | `true` | First launch has no file |

The parent directory is created first (`:62-65`). The pool is
`max_connections(4)` with default min, idle timeout and lifetime
(`crates/store/src/lib.rs:100-104`). `close()` closes the pool and lets WAL
checkpoint on the last connection drop (`:119-122`).

**Migrations run on open for both constructors.** `open` reaches
`from_options` (`:77`, `:100-108`) and `open_in_memory` calls it directly
(`:96`); both land in `sqlx::migrate!("./migrations").run(&self.pool)`
(`:110-113`). There is no separate "migrate" step a caller can forget.

::::warning[`open_in_memory` pins the pool to exactly one connection]
`max_connections(1).min_connections(1).idle_timeout(None).max_lifetime(None)`
(`crates/store/src/lib.rs:88-93`), because "a shared-cache in-memory database
disappears when the last connection closes" (`:86-87`). Raising it to 4 to
match the file-backed pool destroys the database mid-test, intermittently and
confusingly. Do not "optimise" it.
::::

### `StoreError`

Five variants (`crates/store/src/lib.rs:34-49`):

| Variant | Raised by |
| --- | --- |
| `Sqlx(sqlx::Error)` | Any query or connection failure; `#[from]` |
| `Migrate(sqlx::migrate::MigrateError)` | A migration that fails to apply, or a **changed checksum** on an already-applied file |
| `Json { column, source }` | A JSON column that will not parse. Carries the offending column name |
| `NoDataDir` | `directories` could not name a data directory on this platform |
| `Io(std::io::Error)` | Creating the parent directory failed; `#[from]` |

`pub type Result<T, E = StoreError>` (`:51`) is the crate-wide alias every DAO
returns.

`default_database_path()` builds
`ProjectDirs::from("dev", "starlet", "starlet")` and joins `starlet.db` onto its
data directory (`crates/store/src/lib.rs:130-134`), yielding
`<data dir>/starlet/starlet.db`:

| Platform | Path |
| --- | --- |
| Linux | `~/.local/share/starlet/starlet.db` |
| macOS | `~/Library/Application Support/starlet/starlet.db` |
| Windows | `%APPDATA%\starlet\data\starlet.db` |

Documented in place at `crates/store/src/lib.rs:125-129`. A platform with no

### The preserving upsert

The `ON CONFLICT` clause overwrites most columns from `excluded`, but three are
protected because a star-listing refresh cannot know them
(`crates/store/src/repos.rs:198-217`):

- `languages_json = CASE WHEN excluded.languages_json = '{}' THEN repos.languages_json ELSE excluded.languages_json END` (`:208-210`) — an empty map means "no information", not "no languages".
- `contributors_json = coalesce(excluded.contributors_json, repos.contributors_json)` (`:211`); the Rust side maps an empty `Vec` to SQL `NULL` first (`:185-189`).
- `starred_at = coalesce(excluded.starred_at, repos.starred_at)` (`:212`).

`etag`, `readme_md` and `readme_fetched_at` are **not in the INSERT column list
at all** (`:193-197`), so the upsert structurally cannot touch them.

::::danger[`RepoRow` is decoded by index, and `REPO_COLUMNS` is the only record of that order]
`RepoRow` has a hand-written `FromRow` that pulls every field by position
(`crates/store/src/repos.rs:40-63`) rather than by name, because "the derive
looks every column up by name, which at eighteen columns and five thousand rows
costs more than the query itself" (`:14-17`). `REPO_COLUMNS`
(`crates/store/src/repos.rs:65-67`) is the single definition of that order.

Add a column to the `SELECT` list without adding the matching `try_get` to
`from_row` **at the same index** and the row decodes silently wrong: every field
after the insertion point shifts by one. There is no compile error and no
runtime error — just wrong data. Change `REPO_COLUMNS`, `RepoRow` and
`from_row` in one edit, always.
::::

`load_repos` calls `into_repo(false)` (`crates/store/src/repos.rs:137`) and
**never populates `contributors`**; only `load_repo` passes `true` (`:157`).
Reading `repo.contributors` off a list-loaded repo gives you an empty vec, not
the truth.

### Three sources, and who may overwrite whom

The separation is what makes "never overwrite a user tag with an AI tag" a
property of the schema rather than a rule someone has to remember
(`crates/store/src/taxonomy.rs:3-7`).

| Source | Owner | Write path | Lifetime |
| --- | --- | --- | --- |
| `github` | sync | `sync_github_topics`, inside the `upsert_repos` transaction (`crates/store/src/repos.rs:242`) | Replaced wholesale each sync, so a topic removed upstream disappears locally |
| `ai` | an analysis run | `set_ai_tags` | Replaced wholesale each run |
| `user` | the user | `add_user_tag` / `promote_tag` / `remove_tag` | Never deleted by sync or by an AI run |

`set_ai_tags` reads the repo's existing **user** tag names lowercased
(`crates/store/src/taxonomy.rs:117-126`) and skips any incoming AI tag already
in that set (`:128-131`). So for identical names, user beats AI, and the AI
duplicate is dropped rather than stored.

The SQL-level detail — column types, the eight indexes, the five FTS triggers —
lives in [Database schema](/reference/database-schema).

Two traps in this module:

- **`ORDER BY t.source DESC` is a string sort.** Used in both
  `Store::repo_tags` (`crates/store/src/taxonomy.rs:76`) and `all_repo_tags`
  (`crates/store/src/repos.rs:376`), it happens to yield `user` > `github` >
  `ai`, which is the intended precedence, but only by alphabetical accident. A
  fourth source lands wherever its name falls. Related: the fallback
  `TagSource::parse(..).unwrap_or(TagSource::Github)`
  (`crates/store/src/taxonomy.rs:85-86`, `:199-200`,
  `crates/store/src/repos.rs:386-387`) silently relabels an unknown source as
  GitHub.
- **`promote_tag` is two transactions, not one**
  (`crates/store/src/taxonomy.rs:168-171`). `add_user_tag` commits, then
  `remove_tag` commits. A crash between them leaves both a user copy and the AI
  original attached to the repo.

## Full-text search

```rust crates/store/src/fts.rs
const W_FULL_NAME: f32 = 1.0;    // :25
const W_DESCRIPTION: f32 = 5.0;  // :26
const W_TOPICS: f32 = 3.0;       // :27
const W_TAGS: f32 = 4.0;         // :28

pub async fn Store::search_fts(
    &self, terms: &[String], limit: i64,
) -> Result<HashMap<i64, f32>>   // :36
```

The four weights are passed to `bm25()` in **table-declaration order**
(`crates/store/src/fts.rs:42-44`), so the weight list and the FTS5 column list
are a positional pair. `full_name` is deliberately the lowest: "the fuzzy
matcher already owns that field and gets 70 % of the final score. What FTS
contributes that nucleo cannot is the description and the tag vocabulary"
(`:22-24`).

SQLite's `bm25()` is negative, better-is-more-negative. `search_fts` selects
`-bm25(...)` and orders by it descending (`crates/store/src/fts.rs:42-43`), so
the map it returns is positive and bigger-is-better before it reaches the
blend. How that map is combined with the fuzzy score is
[Search pipeline](/architecture/search-pipeline); the arithmetic is
[Ranking](/reference/ranking).

`build_match` (`crates/store/src/fts.rs:77-95`) is the sanitiser. Each term is
filtered to alphanumerics plus `_ - . / "` (`:80-83`), trimmed of
non-alphanumeric edges (`:84`), then emitted as `"term"*` with embedded quotes
doubled (`:88`), and the parts joined with `AND` (`:93`). FTS5 operators the
user typed (`OR`, `NEAR`, `-`, `^`) become data, not syntax (`:74-76`). A
punctuation-only term is dropped (`:85-87`); if every term is dropped the
function returns `None` and `search_fts` short-circuits to an empty map
(`:37-39`).

::::note[A malformed MATCH is not an error]
`sqlx::Error::Database` from the FTS query is logged at `debug` and swallowed
into an empty map (`crates/store/src/fts.rs:53-60`) — "a malformed MATCH
expression is a user typing, not a bug" (`:51-52`). Non-database errors still
propagate. If full-text results vanish for one keystroke, look in the debug log
for `fts match rejected`, not for an exception.
::::

`FtsHit` (`crates/store/src/fts.rs:13-18`) is exported from the crate root
(`crates/store/src/lib.rs:24`) but **never constructed anywhere in this crate** —
`search_fts` returns a `HashMap<i64, f32>` instead.

### Timestamps

```rust crates/store/src/time.rs
pub fn format_ts(ts: &DateTime<Utc>) -> String                 // :10
pub fn parse_ts(raw: Option<&str>) -> Option<DateTime<Utc>>    // :16
```

Every timestamp column is RFC 3339 in UTC. Encoding is explicit rather than
delegated to a driver mapping "so the on-disk representation cannot change
under a dependency bump" (`crates/store/src/time.rs:3-5`) — which is why `sqlx`
has its `chrono` feature enabled and the crate still formats by hand.
`format_ts` is always second precision with a `Z` suffix (`:11`). `parse_ts`
returns `None` for anything unparseable rather than failing: "a bad timestamp
costs a sort key, not a repo" (`:14-15`).

## Key invariants

- **`repos_fts.rowid == repos.id`, always**
  (`crates/store/migrations/0001_init.sql:91`). Everything currently writes the
  FTS table through triggers; a new direct write path must honour it or the
  join key silently points at the wrong repo.
- **There is no `AFTER UPDATE ON repo_tags` trigger.** Insert (`:118`) and
  delete (`:126`) recompute the FTS `tags` column; changing only `confidence`
  does not. Harmless today because the FTS column holds names, not confidences.
- **`repos_fts_update` deliberately does not write `tags`** (`:109-110`), so a
  metadata refresh cannot drop tag text.
- **`prune_orphan_tags` is manual.** `ON DELETE CASCADE` removes the
  `repo_tags` rows but leaves the `tags` row behind
  (`crates/store/src/taxonomy.rs:268-274`); nothing in this crate calls prune
  automatically.
- **`replace_ai_groups` links members by `full_name`**
  (`crates/store/src/taxonomy.rs:230-242`), so a repo renamed between group
  generation and linking is silently dropped from its group. It also deletes
  only `source='ai'` groups (`:213`), so a future user-created group survives.
- **JSON serialisation failures are swallowed.**
  `unwrap_or_else(|_| "{}".into())` in `upsert_repos`
  (`crates/store/src/repos.rs:183`) and `set_languages` (`:317`), `"[]"` in
  `set_contributors` (`:340`), `.ok()` for contributors on upsert (`:188`). In
  practice `BTreeMap<String, i64>` and `Vec<Contributor>` cannot fail to
  serialise; if you add a type that can, it will fail as an empty value rather
  than an error.
- **`upsert_repos` returns summed `rows_affected`**
  (`crates/store/src/repos.rs:240`). For `INSERT … ON CONFLICT DO UPDATE`
  SQLite counts updates too, so this is a "rows touched" count, never an
  "inserted" count.
- **`languages_json = '{}'` and `topics_json = '[]'` are the schema defaults**
  and the common case, so the row decoder short-circuits JSON parsing on them.
  `ids_without_languages` keys off exactly that literal
  (`crates/store/src/repos.rs:327`), which means "backfilled and genuinely
  empty" is indistinguishable from "never backfilled".

## Extension points

- **A schema change** → [Add a migration](/guides/add-a-migration). Never edit
  `0001_init.sql`: `sqlx` checksums applied migrations, and a changed checksum
  becomes `StoreError::Migrate` on every existing install.
- **A new column that sync writes** →
  [Add a synced field](/guides/add-a-synced-field), which walks the wire struct,
  the model, the migration, `REPO_COLUMNS`, `RepoRow`, and the `upsert_repos`
  bind order in one pass.
- **A new `sync_state` key** → add a `pub const KEY_X: &str = "sync.x"` (or
  `"ui.x"`) beside the others at `crates/store/src/state.rs:11-23` and
  re-export it from `crates/store/src/lib.rs:25-28`. No schema change:
  `sync_state` is free-form. Keep it here rather than in the consuming crate
  unless it is genuinely UI-private.
- **A new DAO method** → put it in an `impl Store` block in the module that owns
  the table. Take `&self`. Use `self.pool()` for a single statement and
  `self.pool().begin()` when several statements must be atomic. Return
  `crate::Result<T>` and decode positionally with `row.try_get(<index>)?`. A
  helper that must join an existing transaction takes
  `&mut Transaction<'_, Sqlite>` instead of `&self`, like `sync_github_topics`
  (`crates/store/src/taxonomy.rs:44-48`) and `tag_id` (`:31`).
